# UX改善バックログ

最終更新: 2026-11-10

本アプリの売りは「重くならない画像読み込みと高速な閲覧」。新機能は、起動時間・スクロール・ページ送りに対して追加コストが小さいものを優先する。

## 保留・不採用

| 案 | 判断 | 理由 / 再検討条件 |
| --- | --- | --- |
| サムネイル付きフィルムストリップ | 保留 | 数十枚の追加デコードとメモリ使用が発生し、本アプリの売りと相反する。#37のスクラバーで代替できる |
| 前後2枚以上の先読み | 不採用 | メモリ使用が増える。現在の前後1枚＋Coilキャッシュを維持する |
| 複数選択の一括お気に入り/共有 | 保留 | UIと状態管理が重くなる。共有の単体機能（#40）の利用状況を見て判断 |
| サイズ順ソート | 保留 | 新しい複合インデックスとDBマイグレーションが必要。自然順・更新日時で足りるか確認してから |
| フォルダ名順・サイズ順ソート | 保留 | フォルダ一覧の並び順追加。要望が強ければ既存の`FolderSortMode`を拡張 |
| 画像の削除 | 不採用（現時点） | 破壊的でMediaStoreの権限・ゴミ箱仕様の確認が必要。まずは端末の標準ギャラリーに任せる |
| タグ・アルバム・コレクション | 一部採用 | フォルダへのタグ付与とタグ絞り込みを実装（#46）。タグの階層化・色分けは保留。データモデルは `tags` / `folder_tags` の2テーブル |
| 全フォルダ横断の画像名検索（FTS） | 保留 | 35万件規模のインデックス構築とDB容量増の検証が必要。まずはフォルダ内検索（#39）から |
| クラウド同期・バックアップ | 不採用 | オフライン前提の個人用アプリという方針に反する |
| 動画・GIFの再生 | 対象外 | 画像ビューアの範囲外。必要なら別アプリ/別Issueで検討 |
| 画像編集・フィルタ・EXIF編集 | 対象外 | 閲覧速度優先のため。外部アプリへ共有（#40）で対応 |
| スライドショー・自動再生 | 保留 | 追加のタイマー/先読み制御が必要。閲覧の邪魔をしない形なら再検討 |
| ランダム表示 | 保留 | 大量フォルダでは楽しいが、位置復元や「戻る」の意味が変わる |
| ホーム画面ウィジェット | 保留 | 個人利用では優先度低い。起動高速化の効果を測ってから |
| 日付・月ごとのグループ表示 | 保留 | 大量画像の整理には有効だが、グリッドのレイアウトと列数設定への影響が大きい |
| 2枚の画像比較表示 | 保留 | 個人用途での頻度が不明。UIが大きく、まずは要望を確認 |
| 起動時に前回のビューアを自動で開く | 不採用 | 起動のたびに意図しない画面になる可能性がある。#41はカードから任意に開く形にする |
| 画像背景のぼかし・演出 | 保留 | 見た目は良いが、追加の描画/デコードコストとバッテリー消費の検証が必要 |

## 性能ガードレール

新機能を実装するときは以下を守る。

- 一覧・ビューアの表示で、画面外の画像を大量にデコードしない
- スクロールやドラッグのたびにDB書き込み・MediaStore問い合わせをしない（debounce/離脱時保存）
- 起動時にRoomキャッシュ以外の全件走査を追加しない
- サムネイルは列数・画面サイズに合った解像度でデコードし、フルサイズをメモリに載せない
- 追加する設定は1行の読み書きで済む形にし、起動時のクエリを増やさない
- 機能追加後は `:app:testDebugUnitTest` / `:app:assembleDebug` と実機での起動・スクロール・ページ送りを確認する
