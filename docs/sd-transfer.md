# PC から SD カードへ転送する手順（転送が遅い・失敗するときの対策）

最終更新: 2026-11-13

エクスプローラー（MTP）で SD カードへ直接コピーすると、**転送開始まで待たされる**、
**途中で失敗する**ことがある。本ドキュメントは OPPO Reno13 A（CPH2699）で原因を切り分け、
再現可能な手順と対策をまとめたもの。

- 対象端末: OPPO Reno13 A（CPH2699 / Android 16 / ColorOS 16.0.5）
- SD カード: `EEFF-78C9`（exfat / `/storage/EEFF-78C9` / 空き 12GB 前後）
- 接続: USB 2.0（端末側 Type-C は USB 2.0 相当。PC 側は USB 3.2 ポート）

## 1. 結論（先に知りたいこと）

| 知りたいこと | 結論 |
| --- | --- |
| 自作アプリで MTP の遅さは改善できるか | **できない**。実測で MTP の列挙は「2 項目表示に 493 秒、SD 配下は 334 秒で失敗」。遅さは端末の MTP サーバー（`mediaprovider`）側にあり、通常アプリからは制御できない |
| 今のやり方（LocalSend で内部→SD へ移動）はベストか | **方向は正しい**。ただし zip にまとめて送る方が速い（300 ファイル 29MB で 6.1 秒 / 内部経由 17.8 秒）。LocalSend が速いのは MTP の列挙待ちが無いため |
| 一番速い方法 | **zip にまとめて 1 ファイルで送り、端末内で解凍する**（`scripts\transfer-to-sd.ps1` の既定）。300 ファイル 29MB で 6.1 秒。同じ内容を 1 ファイルずつ SD へ直送すると 8.6 秒、内部へ push 後に SD へ複製すると 17.8 秒 |
| USB 2.0 は原因か | **帯域は上限だが主因ではない**。200MB 単一ファイルで 20.7MB/s と USB 2.0 の実効上限に近い一方、100KB × 300 個は 3.4MB/s しか出ない。**不満の主因は「ファイル数あたりの固定費」**（1 ファイル 200MB は 10.0 秒で安定、100KB × 300 個は 8.6 秒） |
| じゃあどうするのが一番速いか | 小さいファイルが多いなら **zip 化 → 1 ファイルで送る → 端末内で解凍**。数 MB 以上のファイルだけなら Direct（USB 2.0 の帯域で頭打ちになるが、固定費は小さい） |
| 転送後のアプリ反映 | アプリ側の改善余地がある（§6）。MediaStore の更新が遅れるとフォルダ一覧に出ないので、転送後はアプリの**手動更新**を実行する |

## 2. 実測値（2026-11-13 / 同一端末・同一 USB ポート）

すべて `adb` 経由。1 ファイルあたりのサイズと本数を変えて測った。

### 2.1 ファイル数が少ないほど速い

| 内容 | 方式 | 時間 | 実効速度 |
| --- | --- | --- | --- |
| 100KB × 300 個（29.3MB） | SD へ直接 push | 8.6 秒 | 3.4 MB/s |
| 100KB × 300 個（29.3MB） | 内部へ push → 端末内で SD へ `cp` | 17.8 秒 | 1.6 MB/s |
| 100KB × 300 個（29.3MB） | zip 1 ファイルを内部へ push → SD で解凍 | **6.1 秒** | 4.8 MB/s |
| 1MB × 70 個（42.9MB） | 内部へ push → 端末内で SD へ `cp` | 6.6 秒 | 6.5 MB/s |
| 5MB × 10 個（50MB） | SD へ直接 push | 1.8 秒 | 29.7 MB/s |
| 200MB × 1 個 | SD へ直接 push | 10.0 秒 | 20.7 MB/s |

- 1 ファイルが大きいほど帯域を使い切れる。**小さいファイルを大量に送るほど不利**。
- SD への直書きは「1 ファイルあたりの固定費」が大きい（100KB × 300 個で 1 個あたり約 28ms）。
- 内部へ push してから `cp` すると、SD 側で**もう一度 1 ファイルずつ作る**ため固定費が二重に乗る。
  LocalSend が「内部に送ってから SD へ移動」で速く感じるのは、MTP の待ちが無いことと、
  移動が `rename` で済む場合があるため。ただし今回は `mv`（12.8 秒）より `cp`（7.4 秒）が速い場面もあり、
  フォルダ構成や既存ファイル数で変わる。

### 2.2 SD カードは「列挙」も遅い

| 操作 | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- |
| SD 直下（946 エントリ）の `ls` | **47,040ms** | 313ms | 389ms |
| 内部 `Download`（318 エントリ）の `ls` | 201ms | 74ms | 89ms |

- SD 直下は**初回アクセスで 47 秒**かかった。以後はキャッシュされ 300〜400ms。
- MTP は接続のたびに SD のディレクトリを列挙するため、この初回コストを毎回払う可能性が高い。
  「転送が始まるまで時間がかかる」の主因はここ。
- 対策として、**SD 直下のフォルダ数を減らす**（下記 §4）と初回列挙が軽くなる。

### 2.3 MTP（エクスプローラー）は実測でほぼ応答しない

Windows の Shell COM（`Shell.Application`）から MTP 経由で端末を列挙した実測:

| 操作 | 所要時間 | 結果 |
| --- | --- | --- |
| 「OPPO Reno13 A」直下の項目一覧（2 項目） | **493 秒** | 2 項目（内部共有ストレージ / SDカード）を取得 |
| 「SDカード」配下の項目一覧 | **334 秒** | 取得できず（null） |

- **2 項目を表示するだけで 8 分以上**かかった。エクスプローラーで「転送が始まるまで待たされる」
  という体感と一致する。
- SD カード配下は 334 秒待っても列挙できなかった。ここでタイムアウトやエラーになる。
- 端末側の `ls` は 47 秒 → 2 回目以降 0.3 秒なので、**遅さは MTP サーバー側**にある。
  ADB で直接触ればこの待ちは発生しない。

### 2.3 ファイルシステムの違い

| 項目 | SD（exfat） | 内部（f2fs/ext4） |
| --- | --- | --- |
| 100KB ファイルの実占有 | 128KB | 100KB |
| 100KB × 100 個の書き込み | 3,554ms | 2,287ms |
| 100KB の読み出し × 20 | 950ms | 479ms |

- クラスタサイズが 128KB のため、**小さいファイルは容量を約 1.28 倍消費**する。
- 断片化した SD では読み書きがさらに遅くなる。空きが 12GB（使用率 99%）の状態も不利。

### 2.4 USB 2.0 の影響

- 200MB 単一ファイルで 20.7MB/s。USB 2.0 の実効上限（25〜35MB/s 程度）に近く、
  **帯域そのものは USB 2.0 で頭打ち**になっている。
- ただし小さいファイルでは 3.4MB/s しか出ておらず、**帯域より「ファイル数あたりの固定費」が支配的**。
  USB 3.0 のケーブル／ポートに変えても、小さいファイル中心なら劇的には速くならない。
- USB 3.0 化の効果が見込めるのは「数 MB 以上のファイルをまとめて送るとき」。

## 3. 推奨手順（再現可能）

`scripts\transfer-to-sd.ps1` を使う。MTP を経由せず、ADB で転送する。

```powershell
# 1. 端末を USB デバッグ有効で接続し、認識を確認
adb devices -l

# 2. 転送（既定は zip 方式。SD の Pictures\20261113 へ入れる）
powershell -ExecutionPolicy Bypass -File scripts\transfer-to-sd.ps1 `
  -Source D:\pics `
  -Destination Pictures\20261113

# 3. 端末が複数あるときは -Serial を付ける
powershell -ExecutionPolicy Bypass -File scripts\transfer-to-sd.ps1 `
  -Source D:\pics -Destination Pictures\20261113 -Serial 6ad7aa65

# 4. 事前確認だけ（端末を書き換えない）
powershell -ExecutionPolicy Bypass -File scripts\transfer-to-sd.ps1 `
  -Source D:\pics -Destination Pictures\20261113 -DryRun

# 5. 中身を MD5 まで確認する（時間は増える）
powershell -ExecutionPolicy Bypass -File scripts\transfer-to-sd.ps1 `
  -Source D:\pics -Destination Pictures\20261113 -Verify Hash
```

方式の使い分け:

| 方式 | 指定 | 向いている場面 |
| --- | --- | --- |
| Zip（既定） | `-Mode Zip` | 小さいファイルが多い（写真・AI 生成画像・同人誌のページ画像など）。**ASCII 名のみ** |
| Staged | `-Mode Staged` | zip を作りたくない／圧縮済みの大ファイルが多い／**日本語ファイル名を含む** |
| Direct | `-Mode Direct` | 数 MB 以上のファイルが少しだけ。PC の空き容量を使いたくない |

- **日本語などの非 ASCII 名を含むフォルダでは、zip 方式は自動的に Staged へ切り替わる。**
  端末の `unzip` が zip 内の非 ASCII 名を復元できず `Operation not permitted` になるため
  （実測: `サブ フォルダ/テスト_03.jpg` で失敗）。`-Force` を付けると zip のまま実行する。
- スクリプトは**端末側の写真を削除しない**。自分のステージング領域（`/sdcard/Download/PictobiTransfer`）だけを、
  検証に成功したときに削除する。
- 失敗時はステージングを残して終了コード 3 を返す。表示されたパスを確認して手動で消す。
- `-OutputPath captures\transfer.csv` を付けると、工程ごとの所要時間を CSV に残せる。

### 3.1 ADB を使わない場合の最短手順

1. PC でフォルダを zip にまとめる（エクスプローラーの右クリック → 圧縮でもよい）。
2. その zip を**内部ストレージ**（`Download` など）へコピーする（MTP でも 1 ファイルなら待たされにくい）。
3. 端末のファイルマネージャーで zip を SD カードへ移動し、そこで解凍する。
4. 解凍したフォルダを `Pictures` などの目的の場所へ移す。

## 4. エクスプローラー（MTP）を使う場合の対策

ADB を使わないときの対策。すべて実測に基づく。

1. **SD カード直下にフォルダを作らない。** `Pictures/` などの既存フォルダの下へ入れる。
   SD 直下のエントリ数が初回列挙 47 秒の原因だった。946 → 数十に減らせば待ちが短くなる。
2. **まとめて 1 つの zip にしてからコピーする。** エクスプローラーでも zip なら 1 ファイルで済む。
   端末側で解凍する（ファイルマネージャー、または `unzip`）。
3. **一度に大量の小さいファイルを送らない。** 100 個ずつなどに分ける。1 回の接続で全部送ろうとすると
   途中で失敗しやすい。
4. **内部ストレージへコピーしてから、端末のファイルマネージャーで SD へ移動する。**
   質問にある LocalSend と同じ考え方。MTP の待ちを片道にできる。
5. **転送中は端末の画面を消さない／スリープにしない。** MTP は画面ロックやスリープで切れやすい。
6. **SD の空きを確保する。** 使用率 99%（空き 12GB）では書き込みが不安定になる。
   exfat のクラスタが 128KB なので、100KB のファイルは 1.28 倍の容量を食う。
7. **ケーブルはデータ通信対応を使う。** 充電専用ケーブルでは MTP が不安定になる。

## 5. アプリを自作して改善できる範囲

| やりたいこと | アプリで可能か | 理由 |
| --- | --- | --- |
| MTP の転送開始待ちを無くす | **不可** | MTP は端末の `mediaprovider` がホストへ応答する仕組み。通常アプリからは制御できない |
| PC からアプリへ直接送って SD へ書く | 可能 | Wi-Fi 経由の受信サーバー（LocalSend 相当）をアプリ内に持てば、MTP を回避できる。ただし実装コストが高い |
| 転送後の一覧反映を速くする | **可能** | §6 のとおり。`MediaStore` の更新を待たずに自分の DB へ取り込む／スキャンを促す |
| `unzip` をアプリ内で行う | 可能 | zip を受け取って解凍する機能を持てば、PC 側の手順を 1 つ減らせる |
| SD の書き込み速度を上げる | 不可 | ハードとファイルシステム次第。アプリからは制御できない |

**結論:** 転送経路そのもの（MTP の遅さ）を自作アプリで解消することはできない。
アプリで価値を出せるのは「受け取ってすぐ一覧に出す」部分。転送はスクリプト（ADB）か
LocalSend など専用アプリに任せるのが現実的。

## 6. 転送後にアプリへ反映させる

転送しただけでは、アプリのフォルダ一覧に出ないことがある。原因は次の 2 つ。

1. **MediaStore への登録が遅れる／漏れる。** `adb push` や `unzip` で作ったファイルは、
   MediaProvider のスキャンが走るまで `content://media/external/images/media` に出てこない。
   実測では push 直後に 10 件中 10 件が登録されていたが、`dd` で直接作ったファイルは 0 件だった。
   → **アプリの手動更新**を実行する。それでも出ない場合は端末を再起動する。
2. **アプリの同期は差分方式。** `DATE_MODIFIED` が前回同期以降のものだけを拾う。
   転送したファイルの更新日時が古い（コピー元の日時を保持している）と、
   差分では拾えず、24 時間ごとの全件走査まで出ないことがある。
   → 手動更新（全件走査）を使う。

スクリプトは転送後に自動でスキャンを促さない（`content` コマンドの権限に依存するため）。
転送後はアプリの更新ボタンを押す運用にする。

## 7. 実測の再現方法

```powershell
# SD の列挙時間（初回は時間がかかる）
adb -s <serial> shell "s=`$(date +%s%3N); ls -1 /storage/EEFF-78C9 > /dev/null; e=`$(date +%s%3N); echo `$((e-s)) ms"

# 単一ファイルの転送速度
adb -s <serial> push big.bin /storage/EEFF-78C9/pv.bin

# 小さいファイル多数の転送速度
adb -s <serial> push small_dir /storage/EEFF-78C9/pv_dir
```

MTP（エクスプローラー）の列挙時間は、Windows の Shell COM から測れる。
時間がかかるため、失敗しても待ち続けないようタイムアウト付きで実行する。

```powershell
$sh = New-Object -ComObject Shell.Application
$dev = $sh.NameSpace(17).Items() | Where-Object { $_.Name -like 'OPPO*' } | Select-Object -First 1
$root = $sh.NameSpace($dev.Path)
$root.Items().Count     # ここで数分待たされることがある
```

測定後は端末側の検証用フォルダ（`pv*` など）を削除する。スクリプトの検証で作った
`PictobiScriptTest` / `PictobiZipTest` も同様に削除済み。
