既存アプリが遅く感じる理由は、だいたい **「毎回ファイルシステム寄りに確認している」「キャッシュ方針が弱い」「画像表示以外の機能が多い」** からです。

## よくある原因

### 1. 起動時に毎回メディア一覧を再取得している

画像ビューアは起動時に、

```text
MediaStore / フォルダ / SDカード
→ 画像一覧を再取得
→ フォルダごとに集計
→ サムネイル準備
→ 表示
```

のような処理を走らせることがあります。

画像が少なければ気になりませんが、SDカードに大量画像があると遅くなります。

あなたのアプリではここを、

```text
Room DBから即表示
→ 裏で差分更新
```

にするので速くできます。

---

### 2. 「フォルダ一覧」が実は毎回集計されている

フォルダ一覧は単純に見えて、内部ではこういう処理が必要です。

```text
全画像を取得
→ relativePathごとにGROUP BY
→ 最新更新日を計算
→ 件数を数える
→ サムネイル候補を選ぶ
```

これを画面に戻るたびにやると、遅く感じます。

特に、

```text
画像詳細 → 画像一覧 → フォルダ一覧
```

へ戻るたびに再集計されると、「再読み込みしてる感」が出ます。

---

### 3. サムネイル生成が重い

画像一覧表示で一番重いのは、だいたいサムネイルです。

悪い例はこれです。

```text
画像ファイルを読む
→ Bitmapにデコード
→ 縮小
→ 表示
```

これを大量にやると遅いです。

本来は、

```text
表示される分だけ読む
小さいサイズで読む
キャッシュを使う
スクロール中は無理に読みすぎない
```

にする必要があります。

---

### 4. 画像のメタ情報を読みすぎている

既存アプリは便利機能のために、画像表示前にいろいろ読んでいる可能性があります。

例えば、

```text
EXIF
撮影日時
GPS
画像サイズ
動画情報
重複判定
クラウド同期状態
お気に入り状態
アルバム情報
顔認識
```

などです。

あなたの要件では、最初はここまで不要です。

```text
mediaId
uri
fileName
folderPath
dateModified
size
```

くらいで十分です。

---

### 5. UI状態を保持していない

戻ったときに再読み込みっぽくなるのは、UI側の状態破棄も大きいです。

例えば、

```text
FolderListScreenを開く
→ ImageGridScreenへ移動
→ 戻る
→ FolderListScreenが再生成
→ ViewModelも再取得
→ 一覧再ロード
```

という作りだと、毎回読み込みが走ります。

対策は、

```text
ViewModelで一覧データを保持
スクロール位置を保持
DBのFlowを購読
戻っただけではスキャンしない
```

です。

---

### 6. SDカードが普通に遅い

内蔵ストレージよりSDカードは遅いことがあります。

特に遅いのは、

```text
大量の小さいファイルを読む
ランダムアクセスする
サムネイルを大量生成する
フォルダを何度も走査する
```

場合です。

画像2000枚でも、ファイル実体を何度も読めば遅くなります。

なので、あなたのアプリでは **DBにはメタ情報だけ保存して、画像本体は表示される分だけ読む** のが重要です。

---

## 既存アプリが再読み込みする理由

再読み込みはバグというより、設計上こうなっていることが多いです。

```text
外部ストレージは他アプリから変更される
画像が増える/消える可能性がある
SDカードが抜き差しされる可能性がある
DBキャッシュと実ファイルの不整合が怖い
```

だから安全側に倒して、

```text
画面を開くたびに最新状態を確認する
```

実装になりやすいです。

ただ、速さ重視ならこれはやりすぎです。

あなたのアプリでは、

```text
画面表示はキャッシュ優先
正確性は裏側差分スキャンで追従
手動更新も用意
```

がよいです。

---

## 目指すべき思想

既存アプリはおそらく、

```text
正確性・多機能・汎用性 優先
```

です。

あなたのアプリは、

```text
即表示・最低限機能・キャッシュ優先
```

に振り切るべきです。

つまり、

```text
多少最新反映が数秒遅れてもいい
でも画面は即出す
```

という設計です。

これなら既存アプリより体感速度を出しやすいです。
