# Pictobi 仕様書 (v0.3)

更新日: 2026-11-16 / ステータス: MVP実装済み（PR #8、OPPO Reno13 Aで実機検証済み／継続検証中）

アプリの表示名は **Pictobi（ピクトビ）**。リポジトリ名 `fastest-picture-viewer`、`applicationId`、データ保存先は既存インストールの更新互換性を保つため変更しない。

## 1. 目的
Android端末の内部ストレージ・SDカードにある大量の画像を、フォルダ単位で待たずに閲覧する。既存ギャラリーで発生する以下の問題を解消する。
- 起動後、フォルダ一覧の初期読み込みに時間がかかる
- 他アプリから復帰した際、開いていたフォルダは残っても一覧内容が再取得される
- 個別フォルダからフォルダ一覧へ戻る際、再読込中に一覧が一時的に消える

**最重要原則:** 古いキャッシュを即座に表示して、最新化は裏側で実施する。更新開始を理由に表示中リストを空にしない。

## 2. 対象・制約
- **利用者/対象端末:** 開発者本人が所有する **OPPO Reno13 A** のみ。Android/ColorOSバージョン、APIレベル、SDカード有無、端末のメディア件数は実機またはADBで確認して記録する。未確認の端末仕様は決め打ちしない
- **最終ゴール:** 端末にAPKを直接インストールし、本人の画像を快適に閲覧できること。Playストア公開・不特定多数への配布を予定しない
- **非対象:** Play審査対応、機種横断保証、公開配布サイト、クラウド同期、広告、課金、アカウント、過剰なCI/E2E設備
- **運用:** WindowsからGradleでビルド、ADBでOPPO Reno13 Aにインストール。機能更新時も同じapplicationIdと署名鍵で上書きする
- **署名:** 実機で試す段階はデバッグ署名でよい。継続使用向けには専用リリース署名鍵を作り、秘密鍵・パスワードをリポジトリ外に保管/バックアップする。署名が変わると上書きできない場合があり、再インストールはアプリデータ消失の可能性がある
- **表示名/アイコン:** ランチャー表示名は `Pictobi`。adaptive icon（背景・前景・monochrome）と Android 12 以降のスプラッシュ画面を同一デザインで統一する。リポジトリ名・applicationId は変更しない

- 対象: Android専用。Kotlin / Jetpack Compose / Room(SQLite) / Coil / MediaStoreを基本構成とする
- 対象コンテンツ: 端末およびSDカードの画像。少なくとも2,000枚以上を想定し、より大量の件数で計測する
- **検証規模の基準:** 2026-11-16 計測時点で MediaStore 画像 **353,770 枚** / フォルダ **2,667**（`external_primary` と SD カード `eeff-78c9` の 2 ボリューム）。フォルダ数は distinct `bucket_id` の数で、除外フォルダと読み取り不可の画像を差し引く前の値。実数には計測日を併記し、過去の計測記録は日付付きの履歴として残す（書き換えない）
- オフラインで動作。外部サーバへのアップロードは行わない
- Android OSによりバックグラウンドプロセスが終了しても、再起動時に一覧と閲覧位置を復元できること
- Androidバージョンと保存先によってMediaStoreの可視範囲・権限・SDカードの認識状態が異なる。対応APIレベル、SAF併用の要否は実機で検証する

| FR-45 | P1 | 画像一覧の並び順 | フォルダ内画像一覧の並び順を「名前順」「新しい順」「古い順」から選べるようにする。名前順はファイル名の自然順（1, 2, 10 の順）で、既定値。新しい順・古い順は更新日時で並べ、同じ日時は mediaId 昇順で順序を確定させる。並び順は画像一覧全体で 1 つの設定として保存し、次回起動時も保持する。並び順を変えると画像の位置が変わるため、スクロール位置は先頭に戻す。保存値が壊れている場合は名前順へ戻す。日時順は DAO 側で並べ、ORDER BY を引数で切り替えない（インデックスを効かせるため） |
| FR-47 | P1 | フォルダ単位の並び順 | 画像一覧の並び順は、全体の既定（名前順）に加えてフォルダ単位で上書きできるようにする。特定のフォルダだけ更新日時順にしたい、という使い方のため。上書きは表示設定で「全体に従う」または3つの並び順から選び、解除すると全体の既定に戻る。全体の並び順を変えてもフォルダ個別の上書きは維持する。名前順も上書きとして保持できる（全体が新しい順のときに、そのフォルダだけ名前順にするため）。グリッド・ビューアの双方で同じ実効並び順を使い、位置ずれを起こさない。保存値が壊れている場合は上書きを無視し、全体の既定に従う |
| FR-48 | P2 | スクロール位置復元の切り替え | フォルダを開いたときに前回のスクロール位置へ戻すかどうかを、表示設定で切り替えられるようにする。既定は有効（従来の動作）。無効のときは前回位置を読まずに先頭から表示し、スクロール位置も保存しない。無効→有効へ戻したときに古い位置へ飛ばないよう、切り替え時に内部状態をリセットする。設定は保存し、再起動後も維持する |
| FR-49 | P1 | Auto Backup 対応 | タグ・お気に入り・除外フォルダ・表示設定を Android 標準 Auto Backup で復元できるようにする。巨大な Room DB（約295MB）・画像・サムネイルは上限（25MB）を超えるため対象外とし、再生成できないデータだけを `files/auto_backup/auto_backup.json` へ書き出す。書き出しは変更時に非同期・原子的に行い、連続変更はまとめる。起動時に「控えはあるが DB にユーザーデータが無い」場合だけマージ復元する（Auto Backup 復元直後の状態）。実クラウドの実行時刻は OS 任せで、アプリからは保証しない |
| FR-46 | P2 | 通知バナーのスワイプ | 「見つからない画像」の通知バナーを横スワイプで消せるようにする。左右どちらの向きでもよく、一定量（96dp）以上動かして離したときだけ消す。閾値未満なら元の位置へ戻し、誤操作で消えないようにする。消した後は画面外へ流してから非表示にする。この操作は今回の表示だけを控えめにするもので、設定（通知の表示ON/OFF）は変更しない。次に手動更新したときに再び表示する。設定で通知をオフにしている場合は、スワイプの状態に関係なく表示しない |

## 4. キャッシュ設計
1. **Room（永続）**: volume識別子、media ID/URI、フォルダ識別子、表示名、更新時刻、ファイルサイズ、自然順ソートキー、走査世代などを保持。IDはボリュームをまたいでも衝突しないようにする。除外フォルダは別テーブルに保存し、表示クエリで除外する（元画像は削除しない）。自然順ソートキーは `(folderKey, naturalSortKey, sortName, mediaId)` のインデックスで取得し、既存行はフォルダ表示時にキーを生成して保存する（全件一括更新はしない）。フォルダタグは `tags`（`normalizedName` UNIQUE）と `folder_tags`（`folderKey` + `tagId`）の2テーブルで多対多を保持し、フォルダの識別子は images と同じ安定キーを使う。実体を開けなかった画像は `unreadable_images`（`itemId` 主キー + `folderKey` / `volumeName` インデックス）に記録し、`images` は消さずに表示クエリから除外する（FR-36）。フォルダ一覧の集計結果は `folder_summaries` / `folder_representatives` / `folder_summary_state` に保持し、起動時は集計クエリではなくキャッシュを読む（FR-42）。
2. **ディスク（サムネイル）**: 縮小画像をキャッシュ。全件キャッシュを目指すが容量上限と削除戦略を用意し、元画像の複製はしない。
3. **RAM（デコード済み）**: 画面に見える画像とその前後を優先。メモリ圧迫時は解放する。
4. **画面状態（SavedStateHandle/永続ストア等）**: 現在のフォルダ・画像・スクロール基準キーを保存。大きな画像リストを状態保存領域に入れない。

## 5. データフロー
1. 初回起動・権限付与後: MediaStore（必要に応じSAF）を走査してRoomに登録。初回スキャン中は進捗または空状態を示す。
2. 2回目以降: Roomからフォルダ一覧を直ちに描画。読み込み中でも既存データを保つ。
3. フォルダを開く: Roomからそのフォルダの画像一覧を描画。スクロール位置を保存。
4. 戻る/他アプリから復帰: ViewModelが存続すればその状態を再利用。消えていてもRoomと保存済みのナビゲーション情報から復元する。
5. 同期: アプリ起動・適切な変更通知・手動更新などを契機にバックグラウンドで取得。変更分をトランザクションで反映し、更新失敗時に表示データを空にしない。

## 6. 同期と整合性
- MediaStoreの世代情報等を利用可能な環境では差分確認を試みる。利用不可・世代リセット・権限変更時は必要な範囲で再走査する
- ファイル削除判定は、アクセス可能と確認したストレージに対し正常終了した走査結果に基づく。不完全な走査で一括削除しない
- ファイルの移動/改名、SDカード抜き差し、権限失効、画像破損、キャッシュ期限切れを扱う
- キャッシュの画像本体が読めない場合はエラー表示し、別画像の閲覧操作を阻害しない
- MediaStore に実体の無い行が残る端末では、開けなかった画像を記録して表示から除外する。フォルダごと消えている場合は代表と他数件の確認で判定し、生きているフォルダを巻き込まない(FR-36)
- 実体の無い行の整理は、対象ボリュームがマウント済みで、対象が全体の半数以下のときだけ実行する。未マウント時は 1 件も削除しない(FR-37)
- Roomを一覧のSingle Source of Truthとし、UIリストを同期開始時にクリアしない (stale-while-revalidate)

## 7. 性能目標（初期仮説・実測で見直す）
- キャッシュありのフォルダ一覧: 起動から初回表示まで **200ms以下を目標**。端末・データ数別に測定
- フォルダから一覧に戻る際: **読み込みによる空白フレーム0件**
- バックグラウンド復帰/プロセス再生成: キャッシュを優先し、全件再走査の完了待ちを発生させない
- 2,000枚を最低検証セットとし、10,000枚以上・SDカード環境も可能なら試験
- 起動時間、DBクエリ時間、サムネイル表示までの時間、スクロールのカクつき、ピークメモリを計測する

## 8. 非機能・セキュリティ
- メインスレッドでメディア走査・画像デコード・DB重処理をしない
- 画像一覧はページング/遅延描画し、巨大配列を毎回再構築しない
- ストレージ権限は必要最小限。Androidバージョン差と写真の部分アクセスを考慮
- アプリ削除時にキャッシュが消えること、ユーザーがキャッシュをクリアできることを想定
- プライベート画像のメタデータ・サムネイルが共有領域やログに漏れないようにする

## 9. 個人端末での受け入れテスト
**必須の実機:** OPPO Reno13 A（現物）。エミュレーターは事前のUI確認などの補助に限定し、実機の動作/性能を代替しない。

1. Windowsで `gradlew.bat :app:testDebugUnitTest` と `gradlew.bat :app:assembleDebug` に成功すること
2. 端末上でUSBデバッグを有効にし `adb devices` で認識、`adb install -r app/build/outputs/apk/debug/app-debug.apk` でインストールできること
3. 画像アクセス権限を許可/拒否して適切に表示され、実画像が見られること。OS/ColorOSの制限を記録する
4. 画像フォルダ→画像一覧→画像詳細→戻るを反復し、既存一覧が一時的に空にならず、スクロール位置が維持されること（可能なら100往復を自動化）
5. 他アプリへの切替/復帰・アプリ再起動・プロセス再生成後もキャッシュと閲覧位置が復元されること
6. 画像の追加・削除・改名、手動更新、更新失敗時の表示継続を確認すること。SDカードは実機で使用している場合に検証すること
7. 最初は少数の画像で確認し、次に本人の利用状況に応じ2,000枚程度以上で性能を測る。テスト画像を投入する場合は専用フォルダを使い、本人の写真を一括削除しない
8. キャッシュあり起動のフォルダ一覧初回表示は200ms以下を**参考目標**として実機で計測し、計測方法・件数・端末状態を記録する。未達の場合は操作感を優先して改善要否を判断する
9. APK更新時に既存設定とキャッシュが維持されることを確認する。長期利用前にリリース署名鍵の保管と更新手順を確認する

**自動化方針:** AIエージェントがGradleビルド・単体テスト・ADBインストール・ログ取得をスクリプト化。必要ならUI Automator/Maestro等を採用するが、実機手動確認を完全には置き換えない。USBデバッグ許可やOS権限操作など必要な人的操作だけ残す。

**完了判定:** OPPO Reno13 Aで日常の画像閲覧・復帰・画面戻りが安定し、再起動後も使え、更新可能なAPK・ビルド手順・署名鍵の保管方針が整っていれば個人用v1.0とする。ほかの機種対応やストア公開は完了条件に含めない。
